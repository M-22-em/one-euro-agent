## Operating model to reproduce

1. Prioritise existing funded work. Start by checking TaskMarket and Frantic, the two venues in the dated earnings record. Select by actual executable demand, not platform brand. Rejected alternatives can be reconsidered only with fresh evidence.
2. Retrieve the exact task, funding evidence, deadline, AI rules, entry cost, review procedure, payout network and acceptance criteria. Deduplicate by platform and task ID.
3. Select one task with a deliverable that the connected runtime can create and verify. Prioritise existing paid obligations and accepted work over discovery.
4. Claim or obtain assignment before full production when the mode requires it. Competitive bounties may require original work before selection; bound speculative effort, initially at most 30 minutes per task.
5. Produce an original artifact; check every acceptance gate. For code, run relevant checks and inspect actual results. Never describe unexecuted code as tested.
6. Submit through an authenticated authorised platform route. Read back the submission ID, artifact association, acting identity and timestamp. A draft, a scan or a manual handoff is not an autonomous submission.
7. Monitor acceptance and settlement separately. A passed deadline does not establish rejection or payment. Follow current platform rules, not Circadian's historical settlement lag.
8. Reconcile the actual received native asset, fees, API/infrastructure costs and execution obligations. State net EUR only with a documented valuation method and complete known costs; report realised conversion separately. Exclude simulations, unrelated balances and estimated token bonuses.
9. Allocate the next attempt by evidence: accepted paid work and manageable effort. Retain rejected tasks, objections and failures with their causes.
10. Report timestamp, task, deliverable, submission receipt, decision, payment reference, cumulative costs, verified net and next action. No activity or commit quota as a proxy for sales.

## Runtime target

One orchestrator, one secure persistent execution environment, official marketplace clients, protected signing material, existing private evidence store, and existing public repository for authorised documentation.

The orchestrator needs an identified model/API with proven access and cost accounting. The runner needs Node/shell, HTTPS egress, persistent private storage, controlled signing and artifact verification. Installing a marketplace skill does not install or authenticate this entire system.

Keep the existing signing identity where ownership and access are authenticated. A browser login and a CLI wallet are distinct unless a supported linking flow proves otherwise. Do not initialise a replacement wallet merely because the cloud cannot access the original. Never request secrets in chat or expose them in git, Notion, artifacts or logs.

Reuse existing Notion for private commercial evidence. Public git commits may record code and authorised anonymised documentation; they do not prove productive time, acceptance or revenue. Do not publish buyer correspondence.

## Financial and human boundaries

This adaptation creates no new spending authority, infrastructure purchase, wallet transfer, API subscription or legal assent. Reconcile prior authorisations and actual cumulative expenditure before any paid action; an old automation prompt is not independent proof of user consent.

Use secure provider interfaces for credentials and operator acceptance of binding terms. No bypass of service confirmation or AI eligibility. Human interventions must be recorded separately from autonomous execution.
